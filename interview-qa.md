# Data Engineering Interview Q&A Bank
### For: GCS → Airflow (Cloud Composer) → BigQuery ledger pipelines at HSBC (4 YOE, 6 months on this project)

## How to use this bank

Do not memorize these answers word-for-word — interviewers can smell a script, and one follow-up will break it. Instead: (1) read one section per day; (2) for each question, close the file and answer **aloud** in your own words, then compare; (3) mark the ones you fumbled and revisit them after 2 days, then after a week (spaced repetition); (4) for every concept, ask yourself "could I explain *why* this works, not just *what* it is?" — the "why" is what separates a 4-YOE answer from a 1-YOE answer. Where an answer mentions a mechanism (e.g., partition pruning, logical dates), make sure you can draw it on a whiteboard. Anything marked "version-dependent" — say so plainly in the interview; it reads as experience, not weakness.

## 1. Airflow / Cloud Composer

### Q1: What's the difference between a DAG, a task, and an operator in Airflow?

**Strong answer:** A DAG is the overall workflow definition — a directed acyclic graph that declares *what* runs, in *what order*, and on *what schedule*; it contains no business logic itself, just structure and dependencies. A task is a single node in that graph — one unit of work with its own retries, state, and logs. An operator is the *template class* that defines what a task actually does — `BashOperator`, `PythonOperator`, `GCSToBigQueryOperator` — and when you instantiate an operator inside a DAG, that instance *becomes* a task. So the relationship is: operator = reusable class, task = instantiated operator bound to a DAG, DAG = the graph of tasks. It matters practically because state and retries live at the task level: if task 7 of 10 fails, Airflow reruns just that task, which is why we break pipelines into small, independently rerunnable tasks rather than one giant Python function. In our ledger pipeline, "wait for file", "decompress", "load to staging", "validate", "merge to final" are separate tasks precisely so a validation failure doesn't force a re-download.

**Follow-up they'll ask:** "What about a task *instance*?" — A task instance is a task bound to a specific DAG run (a specific logical date), and it's the thing that actually has a state like `success`/`failed`/`up_for_retry`.

**Red flag to avoid:** Saying "a DAG is a Python script that runs my code" — the DAG file is parsed by the scheduler repeatedly; heavy code at module level (API calls, DB queries) slows the whole scheduler down.

### Q2: Explain Airflow's scheduling semantics — what is the execution date / logical date, and why does a daily DAG for "today" run tomorrow?

**Strong answer:** This is the classic Airflow gotcha. Airflow was built around *data intervals*: a scheduled run represents a window of data, and the run fires **at the end of that window**, because only then is the data complete. So a daily DAG with `schedule="@daily"` and a run for the interval 2026-07-14 → 2026-07-15 actually *executes* just after midnight on the 15th, but its `logical_date` (called `execution_date` before Airflow 2.2 — version-dependent naming) is 2026-07-14, the *start* of the interval. In practice: the run that processes "yesterday's ledger file" carries yesterday's date as its logical date even though the wall clock says today. This is why templated values like `{{ ds }}` give you the interval start — perfect for building the file path of yesterday's CSV, e.g. `gs://landing/ledger/{{ ds }}/`. If you ignore this, you get off-by-one-day bugs: the pipeline "runs today" but loads the wrong day's partition. Since Airflow 2.2 the cleaner mental model is `data_interval_start` and `data_interval_end`, which make the window explicit instead of implied.

**Follow-up they'll ask:** "So if I deploy a daily DAG today with `start_date` today, when does the first run happen?" — Tomorrow just after midnight, covering today's interval (assuming catchup rules allow it).

**Red flag to avoid:** Saying "execution_date is when the DAG ran." It is not — it's the start of the data interval, and confusing the two is the single most common Airflow interview fail.

### Q3: What are catchup and backfill, and when would you disable catchup?

**Strong answer:** When a DAG is unpaused, Airflow looks at every scheduled interval between `start_date` and now that hasn't run yet; with `catchup=True` (historically the default — version-dependent, newer configs often default it off) it creates a run for *every* missed interval, in order. Backfill is the manual equivalent: `airflow dags backfill -s 2026-07-01 -e 2026-07-10 my_dag` explicitly creates runs for a date range, typically to reprocess history after a bug fix. Catchup is great when each run is truly interval-parameterized — like our ledger loads, where the run for July 3rd loads July 3rd's file — because you can repair a week of missed loads automatically. You disable catchup (`catchup=False`) when the DAG only ever cares about "latest state," e.g., a job that syncs the current contents of a reference table — running it 30 times for 30 missed days would just do the same work 30 times. The prerequisite for safe catchup/backfill is idempotency: each run must write only its own interval's data, so replays don't duplicate or clobber other days. In finance pipelines we lean on this heavily — a restated ledger file for a past date means backfilling exactly that date, and partition-scoped writes make that safe.

**Follow-up they'll ask:** "How do you backfill just one bad day?" — Clear the existing DAG run for that logical date (or trigger a run with that logical date); Airflow reruns all its tasks with the original interval's templated values.

**Red flag to avoid:** Not knowing that unpausing an old DAG with catchup on can suddenly launch hundreds of runs and swamp your BigQuery quota — mention `max_active_runs` as the guard.

### Q4: Why must Airflow tasks be idempotent, and how do you actually achieve that for a GCS → BigQuery load?

**Strong answer:** Idempotent means running the task twice with the same inputs produces the same end state as running it once. Airflow *will* rerun tasks — retries after transient failures, manual clears, backfills, even scheduler restarts — so a non-idempotent task turns every retry into data corruption, which in a general ledger means double-counted journal entries and a reconciliation break. The main techniques: (1) **partition-scoped overwrite** — load into a date-partitioned BigQuery table using `WRITE_TRUNCATE` on the specific partition decorator (`table$20260714`), so a rerun replaces that day cleanly instead of appending; (2) **delete-then-insert** — a `DELETE WHERE load_date = @ds` followed by insert, in the same run; (3) **MERGE on a natural/business key**, so re-loaded rows update-in-place rather than duplicate; (4) **deterministic inputs** — derive the file path from the logical date (`{{ ds }}`), never from `datetime.now()`, so a rerun next week still targets the same file. Also make side effects rerunnable: "move file to archive" should tolerate the file already being in archive. The interview-worthy framing: retries are a *feature* you design for, not an accident you hope away.

**Follow-up they'll ask:** "Is `WRITE_APPEND` ever safe?" — Only with a downstream dedup step (e.g., staging append + `MERGE`/`ROW_NUMBER()` dedup into final), because append alone duplicates on retry.

**Red flag to avoid:** "We just make sure tasks don't fail." They will fail; the design question is what a rerun does.

### Q5: How do retries, retry_delay, and SLAs work, and how did you configure them?

**Strong answer:** Every task can declare `retries` (how many reattempts), `retry_delay` (wait between attempts), and optionally `retry_exponential_backoff` with `max_retry_delay` so repeated failures back off instead of hammering a struggling service. Retries handle *transient* failures — a GCS blip, a BigQuery 503, a network timeout — which are common in cloud environments; typical config for a load task is 2–3 retries with a 5-minute delay. The key discipline is pairing retries with idempotency (previous question), otherwise each retry risks duplicating data. SLAs in Airflow are a *monitoring* signal, not an enforcement mechanism: `sla=timedelta(hours=2)` means "if this task hasn't finished within 2 hours of the run's expected start, record an SLA miss and fire the `sla_miss_callback`/email" — the task keeps running. In finance this maps to business deadlines: the GL output must reach downstream by a cutoff time, so an SLA miss pages us early enough to intervene before the business deadline, rather than discovering it at close. Worth noting plainly: classic SLA behavior has quirks (it's relative to the scheduled time, not task start) and Airflow has been reworking/deprecating it in newer versions — version-dependent — so many teams implement deadline alerting with a sensor/timeout or external monitoring instead.

**Follow-up they'll ask:** "Difference between `execution_timeout` and SLA?" — `execution_timeout` actually kills the task when exceeded; SLA only alerts.

**Red flag to avoid:** Claiming an SLA stops or fails the task — it doesn't.

### Q6: What are sensors? Explain poke vs reschedule mode and deferrable operators.

**Strong answer:** A sensor is a task that waits for a condition to become true — for us, `GCSObjectExistenceSensor` waits for the day's ledger file to land in the bucket before the pipeline proceeds. In **poke mode** (default), the sensor occupies a worker slot for its entire wait, sleeping between checks (`poke_interval`) — simple, but if you have 20 sensors waiting hours for files, you've parked 20 worker slots doing nothing, which can starve real work. In **reschedule mode**, the sensor checks the condition, then *releases* its slot and asks the scheduler to reschedule it after the interval — between checks it consumes nothing, at the cost of scheduling overhead, so it's the right choice for long waits with infrequent checks. **Deferrable operators** (Airflow 2.2+, version-dependent) go further: the task suspends itself entirely and hands the wait to a separate lightweight process called the **triggerer**, which uses async I/O to watch thousands of conditions concurrently; when the event fires, the task resumes on a worker. `GCSObjectExistenceSensor` supports `deferrable=True`. The mental ladder: poke = cheap to set up, expensive to run; reschedule = frees workers, checks are coarse; deferrable = most efficient at scale but requires the triggerer component (Composer 2 includes it). Always set a `timeout` on sensors so a file that never arrives fails loudly instead of waiting forever.

**Follow-up they'll ask:** "Sensor `timeout` vs `poke_interval`?" — `poke_interval` is time between checks; `timeout` is the total wait budget before the sensor fails (and `soft_fail=True` skips instead of fails).

**Red flag to avoid:** Not mentioning worker-slot exhaustion — it's the entire reason the three modes exist.

### Q7: What is XCom, what are its limits, and why shouldn't you pass a DataFrame through it?

**Strong answer:** XCom ("cross-communication") lets tasks exchange small pieces of data: a task pushes a value (return values of Python callables are auto-pushed), and downstream tasks pull it, typically via templating like `{{ ti.xcom_pull(task_ids='list_files') }}`. Crucially, XComs are stored in the **Airflow metadata database**, serialized (JSON by default) — so they're for *metadata*, not data: a filename, a row count, a table name, a small list of paths. Passing a DataFrame means serializing megabytes or gigabytes into a Postgres row on every run — you'll hit size limits (backend-dependent, roughly ~1 GB hard ceiling on Postgres but practically you should stay in kilobytes), bloat the metadata DB that the scheduler itself depends on, and slow everything down. The correct pattern is **pass references, not payloads**: task A writes the data to GCS or a BigQuery staging table, then pushes the *path or table name* via XCom; task B reads from there. In our pipeline, the "list new files" task pushes the list of GCS URIs, and the load task consumes those URIs — the actual bytes never touch Airflow. There's also a custom XCom backend feature that transparently stores large XComs in GCS, but the cleaner habit is simply designing tasks around shared storage.

**Follow-up they'll ask:** "How does the TaskFlow API relate to XCom?" — `@task`-decorated functions pass return values to each other, and under the hood that *is* XCom, so the same size discipline applies.

**Red flag to avoid:** "We pass the dataframe between tasks" — instant signal that you've only used Airflow as a script runner.

### Q8: What are TaskGroups and why use them?

**Strong answer:** A TaskGroup is a purely organizational construct that nests related tasks under a collapsible box in the UI and gives them a shared id prefix — e.g., a `validate` group containing row-count check, schema check, and amount-reconciliation tasks. Unlike the old SubDagOperator, a TaskGroup is *not* a separate DAG and has no scheduling machinery of its own — all tasks stay in the parent DAG, so there's none of the deadlocking and slot-consumption pain SubDAGs were notorious for; SubDAGs are deprecated and TaskGroups are the replacement. You can set dependencies on the whole group (`extract >> validate_group >> publish`), which keeps DAG code readable when a pipeline has 30+ tasks. They also compose well with loops: generating one TaskGroup per source file or per ledger entity gives a clean, repeated structure in the graph view. The interview point: TaskGroups are about human readability and code organization; they change nothing about execution semantics.

**Follow-up they'll ask:** "Why were SubDAGs bad?" — Each SubDAG ran as its own DAG with its own scheduling and, historically, a SequentialExecutor default — causing deadlocks and wasted slots.

**Red flag to avoid:** Treating TaskGroups as if they provide isolation or separate retries at group level — retries remain per-task.

### Q9: How does branching work in Airflow, and where have you used it?

**Strong answer:** Branching lets a DAG choose a path at runtime: a `BranchPythonOperator` (or `@task.branch`) runs a Python function that returns the task_id (or list of task_ids) to follow, and Airflow marks all non-chosen downstream branches as **skipped**. The classic gotcha is the join: a downstream task that sits after both branches will also be skipped by default, because its default `trigger_rule` is `all_success` and a skipped parent isn't a success — you fix it with `trigger_rule="none_failed_min_one_success"` (or `none_failed`) on the join task. Real uses in a file pipeline: "if today's file is a ZIP, go through the decompress branch, else load directly"; "if the file is empty or absent on a weekend/holiday, branch to a no-op path that still marks the run green"; "if validation fails thresholds, branch to quarantine-and-alert instead of publish." There's also `ShortCircuitOperator` for the simpler "continue or skip everything downstream" case. Branching keeps conditional logic *visible in the graph* rather than buried inside a Python function, which matters for on-call engineers reading the UI at 2 a.m.

**Follow-up they'll ask:** "What trigger rules do you know besides all_success?" — `all_failed`, `one_success`, `none_failed`, `all_done` (run regardless — good for cleanup/notification tasks).

**Red flag to avoid:** Forgetting the trigger-rule fix at the join — it's the follow-up nearly every interviewer asks.

### Q10: How do you handle late-arriving files in a daily pipeline?

**Strong answer:** Layer the defenses. First, a sensor in reschedule/deferrable mode with a generous `timeout` absorbs *normal* lateness — if the upstream system usually delivers by 02:00 but sometimes slips to 05:00, a sensor waiting up to N hours handles that without human involvement. Second, decide explicitly what happens at timeout: fail loudly with an alert (right for critical ledger files where downstream has a hard cutoff), or `soft_fail=True` to skip the day and let a later reconciliation catch it (right for optional feeds). Third, design for *very* late files — the file for the 12th arriving on the 14th: because our loads are keyed to the logical date and partition-scoped, we simply clear/rerun the DAG run for the 12th (or trigger a backfill for that date), and it loads into the 12th's partition idempotently without disturbing the 13th and 14th. Fourth, for chronically unpredictable arrivals, switch the trigger model entirely: event-driven ingestion via GCS notifications → Pub/Sub → triggering the DAG, so the pipeline reacts to the file rather than guessing when it will show up. Finally, keep a daily reconciliation report of expected-vs-received files so a silently missing day can never go unnoticed — in finance, an absent file is as dangerous as a wrong one.

**Follow-up they'll ask:** "What if a *corrected* version of an already-loaded file arrives?" — Treat it as a reprocess: rerun that logical date's pipeline; partition overwrite/MERGE makes the correction replace the original cleanly, and keep the old file in archive for audit.

**Red flag to avoid:** "We just increase the sensor timeout" — that handles lateness but not correction or multi-day gaps.

### Q11: What is dynamic task mapping and when is it better than a loop in the DAG file?

**Strong answer:** Dynamic task mapping (Airflow 2.3+, version-dependent) creates a variable number of parallel task instances at *runtime* based on data: `load_file.expand(uri=list_files_task)` produces one mapped task instance per file that actually landed today. A Python `for` loop in the DAG file, by contrast, is evaluated at *parse time* — the number of tasks is fixed when the scheduler parses the file, so it can't adapt to "today there were 7 files instead of 5," and you'd be tempted to hack it by listing the bucket at parse time, which hits GCS on every scheduler parse loop (bad). With mapping, the upstream task returns the list, and Airflow fans out; each mapped instance retries independently, so one corrupt file fails alone while six load fine — much better blast-radius than one task looping over all files internally. You can cap the fan-out with `max_active_tis_per_dag` and inspect each mapped instance separately in the UI. For our ledger drops, where the number of CSVs inside the daily delivery varies, this is exactly the right tool: list-files task → mapped decompress/load tasks → single join/validate task.

**Follow-up they'll ask:** "What happens if the list is empty?" — The mapped task gets zero instances and is marked skipped (behavior configurable); design the join task's trigger rule accordingly.

**Red flag to avoid:** Confusing runtime mapping with parse-time loops — the distinction is the whole point of the feature.

### Q12: What does Cloud Composer give you over self-managed Airflow?

**Strong answer:** Composer is Google's managed Airflow: it runs the scheduler, workers, webserver, triggerer, and metadata database for you on managed infrastructure — Composer 2 runs on GKE Autopilot with autoscaling workers, so worker capacity scales with load instead of being fixed. Concretely you get: environment lifecycle management (create/upgrade Airflow versions through the console/gcloud/Terraform rather than hand-rolling Helm charts); a **DAGs bucket** — you deploy by copying DAG files to a GCS bucket and Composer syncs them to the environment, which makes CI/CD a simple `gsutil rsync`; `requirements`-style PyPI dependency management on the environment; built-in integration with Cloud Logging and Cloud Monitoring, so task logs and scheduler metrics land in Google's ops stack with alerting; and IAM/service-account integration, so operators like `GCSToBigQueryOperator` authenticate via the environment's service account with no key files. What it does *not* remove: you still own DAG quality, idempotency, sizing decisions (environment size, worker counts/limits), and cost — Composer environments run 24/7 and aren't cheap, which is why teams consolidate many DAGs into one environment. The trade-off summary: you give up some low-level control (and pay a premium) to avoid operating a distributed system whose failure would take down every pipeline in the team.

**Follow-up they'll ask:** "Composer 1 vs 2?" — Composer 2 = GKE Autopilot, autoscaling, Airflow 2 only; Composer 1 is legacy with static worker pools (and Composer 3 has since further abstracted the infrastructure — version-dependent).

**Red flag to avoid:** Not knowing the DAGs-bucket deployment model — it's the most visible day-to-day difference.

### Q13: How do you monitor failed DAGs and set up alerting in Composer?

**Strong answer:** Multiple layers. At the task level: `on_failure_callback` (and DAG-level `on_failure_callback`) fire a Python function on failure — ours posts to a team channel / sends email with the task, logical date, and log URL; `email_on_failure` with SMTP config is the simpler variant. At the run level: SLA-style deadline alerts (or an explicit "deadline check" task) catch pipelines that are *late* rather than failed — in finance, late is almost as bad as broken. At the platform level, Composer exports metrics to **Cloud Monitoring** — scheduler heartbeat, number of queued/failed tasks, worker pod health — and we set alert policies on things like "any DAG run failed" or "scheduler heartbeat missing," which catches whole-environment problems that no per-task callback would fire for (if the scheduler is down, callbacks don't run — that's the key insight). Logs go to **Cloud Logging**, so you can build log-based alerts on specific error patterns. Operationally, the failure-handling loop is: alert → open task logs from the UI/Logging → diagnose (transient vs data vs code) → for transient, clear the task to rerun; for data issues, fix and rerun the affected logical dates, relying on idempotency. A dashboard of last-run status per critical DAG plus expected-file reconciliation completes the picture.

**Follow-up they'll ask:** "How do you catch a DAG that silently stopped being scheduled?" — Freshness/absence alerting: alert if no successful run for DAG X in Y hours — failure callbacks can't catch what never ran.

**Red flag to avoid:** Only mentioning email-on-failure; it misses scheduler outages and late-but-green pipelines.

### Q14: Explain Airflow's parallelism and pool concepts.

**Strong answer:** Airflow throttles concurrency at several nested levels, and knowing which knob is which matters when things queue mysteriously. Globally, `parallelism` caps the total number of task instances running across the whole installation (per scheduler, config-level). Per DAG, `max_active_tasks` (formerly `dag_concurrency` — version-dependent naming) caps concurrent tasks within one DAG's runs, and `max_active_runs` caps how many *runs* of that DAG execute simultaneously — critical during backfills so 30 historical days don't run at once. Per task, `max_active_tis_per_dag` limits parallel instances of one (often mapped) task. **Pools** are named slot buckets that protect shared resources: you create a pool `bigquery_loads` with, say, 5 slots, assign it to every BigQuery load task across all DAGs, and Airflow guarantees at most 5 such tasks run concurrently no matter how many DAGs want to load — this is how you respect external quotas (BigQuery load-job limits, an API's rate limit) without hard-coding coordination between DAGs. Tasks also carry `priority_weight`, which decides who gets a slot first when a pool is contended. The practical debugging sequence when tasks sit in "queued": check pool slots, then `max_active_runs`/`max_active_tasks`, then worker capacity — in that order.

**Follow-up they'll ask:** "Backfill floods your BigQuery quota — what do you change?" — Put the load tasks in a small pool and set `max_active_runs` low on the DAG; the backfill then trickles through safely.

**Red flag to avoid:** Answering only "we add more workers" — most concurrency incidents are configuration, not capacity.

## 2. BigQuery internals & design

### Q15: Describe BigQuery's architecture at a high level.

**Strong answer:** BigQuery separates storage and compute completely, connected by a fast internal network. Storage is **Colossus**, Google's distributed file system, where tables live in a columnar format (Capacitor) — replicated, encrypted, and priced separately from queries. Compute is **Dremel**, a massively parallel query engine: when you run a query, it's compiled into an execution tree of stages, and the work is spread across **slots** — a slot being one unit of compute (roughly a virtual CPU with memory) that processes a piece of a stage; a big query might use thousands of slots for seconds. Between stages, intermediate results move through Google's **shuffle** tier (which leans on fast in-memory/disaggregated infrastructure), so joins and aggregations repartition data without you managing anything. Because storage and compute are decoupled, you can have petabytes stored while paying compute only when querying, scale reads without provisioning clusters, and share data without copies. The user-visible consequences: there are no indexes to manage — performance comes from scanning less (columnar + partitioning + clustering) and shuffling less; and capacity is elastic — on-demand queries borrow from a large shared slot pool, while reservations give you dedicated slots. This serverless model is exactly why it fits a finance team: no cluster ops, and audit/history features are built in.

**Follow-up they'll ask:** "What's a slot, precisely?" — A unit of query compute (CPU+memory); queries are broken into stages whose work units are scheduled onto available slots, and BigQuery dynamically re-plans stage parallelism as the query runs.

**Red flag to avoid:** Describing BigQuery as "a big Postgres" — no indexes, no traditional buffer pool; the columnar/scan-based model changes how you optimize everything.

### Q16: Why is columnar storage central to BigQuery, and why is SELECT * expensive?

**Strong answer:** In columnar storage, all values of one column are stored together, rather than row by row. Analytics queries typically touch few columns but many rows — `SUM(amount) GROUP BY account` reads two columns — so a columnar engine reads only those columns' bytes from disk and skips the rest entirely, often cutting I/O by 10–100x versus row storage. Columns also compress far better because similar values sit adjacently (run-length and dictionary encoding shine on repetitive ledger fields like currency codes or entity IDs). BigQuery's pricing makes this concrete: on-demand queries are billed by **bytes scanned**, and bytes scanned is determined by which columns (and partitions) you touch. `SELECT *` reads every column of every row in scope — so on a wide ledger table with 80 columns, selecting all of them to use three multiplies both cost and time by whatever fraction of the table those 77 unneeded columns represent. Worse, `LIMIT 10` does **not** help: pricing is based on columns/partitions scanned, not rows returned, so `SELECT * ... LIMIT 10` on a 2 TB table bills close to 2 TB. The habits that follow: name your columns, check the query validator's bytes-scanned estimate before running, and use the table preview (free) instead of `SELECT *` for eyeballing data.

**Follow-up they'll ask:** "When does LIMIT reduce cost?" — Effectively only with clustered tables (it can stop scanning early — behavior nuance) or when applied after already-pruned partitions; as a rule, treat LIMIT as a display tool, not a cost tool.

**Red flag to avoid:** Saying LIMIT reduces the bill — a classic tell of someone who hasn't watched the bytes-scanned number.

### Q17: Partitioning vs clustering — how do they differ, and how would you prove partition pruning works?

**Strong answer:** **Partitioning** physically splits a table into segments by one column — ingestion time, a DATE/TIMESTAMP column, or an integer range — and a filter on that column lets BigQuery skip entire partitions before scanning ("pruning"). **Clustering** sorts data *within* each partition (or table) by up to four columns, so filters and aggregations on those columns read fewer blocks; it also helps join and GROUP BY locality. Use partitioning for the dominant coarse filter — for ledger data, the posting/load date, since almost every query says "for this day/month"; use clustering for the next most common filters — account number, entity, currency. Differences that matter: partitions have a hard limit (up to 10,000 per table — check current limits, version-dependent), give *guaranteed*, predictable pruning, and enable partition-level operations (overwrite one day, expire old partitions); clustering has no extra cost or hard column-cardinality limit, is automatically re-clustered in the background for free, but its benefit is best-effort — the estimator may not even show the savings up front. **Proof of pruning:** run the same query twice — with and without the partition filter — and compare "bytes processed" in the job statistics (or the dry-run estimate): the filtered query should show roughly (partitions touched / total partitions) of the bytes. E.g., one day out of two years of daily partitions ≈ 1/730th of the bytes. You can also set `require_partition_filter=true` on the table so nobody can accidentally full-scan it.

**Follow-up they'll ask:** "Why does wrapping the partition column in a function break pruning?" — Pruning needs a filter directly comparable to partition boundaries; `WHERE DATE(ts_col) = '...'` on some setups, or filtering via a joined subquery value, can prevent static pruning — filter on the raw partition column with constant expressions.

**Red flag to avoid:** Saying "clustering is like an index" and stopping there — say it's *physical sort order within storage blocks*, best-effort, auto-maintained.

### Q18: Explain BigQuery's pricing models — on-demand vs capacity — and how you'd control cost.

**Strong answer:** Two compute pricing models. **On-demand:** you pay per TB of bytes scanned by each query (storage billed separately); zero commitment, great for spiky or low volume, but a careless full-table query on a big table is real money, and heavy steady usage gets expensive. **Capacity-based (editions/reservations):** you buy slots — a dedicated amount of compute — billed per slot-hour, with optional autoscaling and 1/3-year commitments for discounts; queries then don't cost per byte, they just contend for your slots, which flips the incentive from "scan less" to "keep slots utilized and queries efficient so they finish faster." Rule of thumb: consistent heavy workloads → capacity is cheaper and gives predictable spend; occasional analytics → on-demand. Cost controls I'd actually use: partition + cluster the big tables and set `require_partition_filter`; use dry-run/estimator before big queries; set `maximum_bytes_billed` on queries or per-user custom quotas so a fat-finger query dies instead of billing terabytes; avoid `SELECT *`; materialize commonly re-scanned subresults; and watch `INFORMATION_SCHEMA.JOBS` for the most expensive queries/users. Also note load jobs, in the classic batch path, are *free* compute-wise — a reason batch loading is the default for daily files. Exact prices and edition names change — version-dependent — so quote the model, not the dollar figures.

**Follow-up they'll ask:** "What's slot contention look like and how do you see it?" — Queries queue/slow down when demand exceeds reservation; inspect via administrative resource charts / `INFORMATION_SCHEMA.JOBS_TIMELINE` showing slot usage over time.

**Red flag to avoid:** Not knowing bytes-scanned is the on-demand billing unit — everything about BigQuery cost hygiene flows from that.

### Q19: Compare streaming inserts, batch load jobs, and the Storage Write API.

**Strong answer:** **Batch load jobs** (`bq load`, `GCSToBigQueryOperator`) ingest files from GCS in bulk: free compute, atomic per job (the job either commits or doesn't), supports CSV/JSON/Avro/Parquet/ORC, subject to daily load-job quotas per table — the default and right answer for daily ledger files. **Legacy streaming inserts** (`insertAll`) push rows one-by-one/in small batches for near-real-time availability: you pay per GB streamed, rows land in a streaming buffer where they're queryable quickly but have historically had caveats (buffered data and DML interactions, best-effort dedup via `insertId`) — legacy now, largely superseded. The **Storage Write API** is the modern replacement: a gRPC-based, high-throughput write path with real semantics — default stream for at-least-once streaming, or application-created streams with offsets giving effectively **exactly-once** writes, plus committed vs pending modes where pending lets you buffer writes and commit them **atomically** across a batch (even across multiple streams) — and it's cheaper than legacy streaming. Decision framework: files arriving on a schedule → batch load (free, atomic, simple); sub-minute freshness needs → Storage Write API; `insertAll` → only for legacy code you haven't migrated. For our pipeline, batch loads win: daily granularity, atomicity per file, zero streaming cost, and clean interplay with partition overwrites for reruns.

**Follow-up they'll ask:** "Why not stream the ledger rows as they're produced?" — Finance wants complete, cut-off-bounded, reconcilable daily sets; streaming adds cost and dedup complexity for freshness nobody downstream needs.

**Red flag to avoid:** Treating streaming as "just faster loading" — the semantics (dedup, atomicity, buffer behavior) are the real differences.

### Q20: How do MERGE and DML work in BigQuery, and what quota/behavior gotchas exist?

**Strong answer:** BigQuery supports full DML — INSERT, UPDATE, DELETE, and MERGE — executed as queries over columnar storage: since files are immutable, a DML statement rewrites the affected storage under the hood rather than editing rows in place, which is why DML is efficient in bulk but wasteful row-at-a-time. **MERGE** is the workhorse for upserts: `MERGE target USING source ON keys WHEN MATCHED THEN UPDATE WHEN NOT MATCHED THEN INSERT` — one atomic statement that makes staging-to-final publication idempotent (rerunning the merge with the same staging data converges to the same target state). Gotchas worth naming: historically BigQuery had strict daily DML-per-table quotas; modern BigQuery treats DML much more generously (mutating statements queue rather than hard-fail in many cases — version-dependent, so check current limits), but the design lesson stands — **set-based, few, large DML statements**, never a loop of single-row UPDATEs. Concurrency: BigQuery uses snapshot isolation; concurrent mutating DML against the same table serializes or conflicts, so pipelines should funnel writes to a table through one path (our Airflow pool of 1 for the final-table merge does exactly this). Also: a MERGE whose `ON` clause matches multiple source rows to one target row errors out — dedupe staging first (`ROW_NUMBER()` by business key, keep latest). And DML over required-partition-filter tables must include the filter, which conveniently also limits the rewrite scope and cost.

**Follow-up they'll ask:** "MERGE vs DELETE+INSERT for reprocessing a day?" — For full-day replacement, partition overwrite (`WRITE_TRUNCATE` on `table$YYYYMMDD`) is cheapest and simplest; MERGE wins when only some rows change or keys must be preserved.

**Red flag to avoid:** Proposing row-by-row updates from a loop — the single biggest anti-pattern in a scan-based warehouse.

### Q21: What are materialized views in BigQuery and when would you use one?

**Strong answer:** A materialized view (MV) precomputes and stores the result of a query over base tables, and — the key part — BigQuery keeps it **automatically and incrementally refreshed**: as base tables get new data, the MV updates in the background, and queries against the MV read mostly precomputed results plus a small delta, cutting both latency and bytes scanned. Even better, the optimizer performs **smart tuning**: a query written against the *base table* can be transparently rewritten to read the MV when it's cheaper — users don't even need to know the MV exists. Constraints (version-dependent, they've loosened over time): the MV query must be from a supported shape — historically aggregations over a single table, with joins/some constructs gaining support later; no full arbitrary SQL; there are freshness/staleness settings (`max_staleness`) trading recency for cost. Use cases for us: a daily-balance-by-account aggregate over the journal-lines table that dashboards hit constantly — the MV turns a repeated multi-GB aggregation into a cheap read. Compare alternatives: a **logical view** saves no compute (re-runs the SQL each time); a **scheduled-query table** is fully materialized but goes stale between runs and needs orchestration; the MV sits in between — always fresh, zero orchestration, but limited SQL. There is a storage + refresh-compute cost, so it pays off when read frequency is high relative to write volume.

**Follow-up they'll ask:** "MV vs BI Engine?" — BI Engine is an in-memory acceleration layer for dashboards; MVs reduce work at the query-plan level — they compose, not compete.

**Red flag to avoid:** Confusing materialized views with ordinary views — "it's a saved query" describes the wrong one.

### Q22: What are external tables over GCS, and when are they the right/wrong tool?

**Strong answer:** An external (federated) table is a table *definition* in BigQuery whose data stays in GCS — CSV, JSON, Avro, Parquet, ORC — queried in place without loading. **BigLake** tables are the evolved form with finer access control and better performance. Right tool when: you want to inspect or validate raw landed files with SQL before committing to a load ("query the landing zone"); data is queried rarely so paying load/storage in BigQuery isn't worth it; or another system owns the files and BigQuery is just one consumer. Wrong tool for hot, repeated analytics: external reads are slower than native storage (no Capacitor optimizations; pruning depends on hive-style partition layout of the files rather than real partitions), some features are limited (historically no time travel/DML on external data), and performance depends on file format and sizes — a folder of thousands of small CSVs will crawl. In our pipeline, a legitimate pattern is an external table over the day's landed CSVs used by a validation task — check row counts and schema *before* loading — then a proper batch load into the native, partitioned table for everything downstream. The mental model: external tables trade query performance and features for zero ingestion latency and single-copy storage.

**Follow-up they'll ask:** "How does partitioning work for external data?" — Via hive-style directory layout (`.../dt=2026-07-14/...`) declared as a source URI prefix, which enables pruning on the `dt` pseudo-column.

**Red flag to avoid:** Suggesting external tables as the *serving* layer for heavy downstream consumption — that's what native, partitioned, clustered tables are for.

### Q23: What is BigQuery time travel and how have you used it operationally?

**Strong answer:** BigQuery retains every table's historical state for a window — default 7 days, configurable down to 2 (version-dependent) — and you can query it with `FOR SYSTEM_TIME AS OF timestamp`, or restore by copying that snapshot over/next to the current table (`bq cp table@<epoch_millis> table_restored`). Operationally, it's the undo button for data incidents: if a bad MERGE corrupts today's GL output, you can (1) *diff* current vs pre-merge state with SQL to quantify exactly what changed — invaluable for an incident report in finance — and (2) restore the pre-merge snapshot in minutes without any backup infrastructure. It also covers dropped tables within the window (undelete via copy from a timestamp before the drop). Limits to state plainly: the window is short — it's an *operational* recovery tool, not an audit archive; for long-term point-in-time needs you use **table snapshots** (cheap, storage-billed-on-delta copies at a moment in time) or keep the immutable source files in the archive bucket, which in our design is the true system of record for replays. One more nuance: time travel interacts with storage billing (deleted data is still billed within the window) and doesn't apply to external tables.

**Follow-up they'll ask:** "Bad load overwrote a partition an hour ago — exact recovery steps?" — Query `FOR SYSTEM_TIME AS OF` just before the load to verify the good state, copy that snapshot to a recovery table, then overwrite the partition from it; afterwards, rerun the correct load idempotently.

**Red flag to avoid:** Calling time travel your "audit trail" — auditors need years, time travel gives days.

### Q24: What are the best practices and risks when loading CSVs into BigQuery?

**Strong answer:** CSVs are the most fragile format BigQuery loads, so the discipline is: **never trust autodetect in production**. Schema autodetection samples a subset of rows to guess types — a column of numeric-looking account codes becomes INT64 and then a row with a leading zero or an alphanumeric code breaks the load (or worse, silently loses the leading zero); a date column with mixed formats becomes STRING one day and DATE another, so the target schema drifts. Production pattern: pin an **explicit schema**, load into a staging table with *lenient/stringy* types, then cast with validation into the typed final table — so type failures become visible bad rows, not load failures. Key load options to know: `skip_leading_rows` for headers; `max_bad_records` to tolerate N malformed rows (use 0 for finance-critical loads — you want to *know*); `allow_jagged_rows` to accept rows with missing trailing columns as NULLs (dangerous for ledger data — a truncated row could silently null an amount; keep it off and fail loudly); `allow_quoted_newlines` for fields containing line breaks (needed for free-text description fields, but it disables parallel splitting of the file, slowing large loads); `field_delimiter`/`quote` for regional quirks (semicolon-delimited European exports); and encoding (UTF-8 vs ISO-8859-1 — mojibake in counterparty names is a classic). Also: gzip CSVs load natively but can't be split for parallelism; and always capture the load job's stats (rows loaded, bad records) for reconciliation against the source manifest.

**Follow-up they'll ask:** "Why load to staging as strings first?" — It separates *ingestion* failures from *validation* failures: the file always lands, and you can query, quantify, and quarantine bad rows with SQL rather than digging through a failed job's opaque error list.

**Red flag to avoid:** "We use autodetect and it works fine" — every experienced interviewer has a scar that says otherwise.

### Q25: Nested/repeated fields (denormalization) vs a star schema in BigQuery — how do you choose?

**Strong answer:** BigQuery natively supports STRUCTs (nested records) and ARRAYs (repeated fields), so you can model a journal *entry* as one row containing a repeated field of its *lines* — parent and children co-located in one table, queried with `UNNEST`. The engine is built for this: co-locating children with parents removes the join entirely, which is often the biggest win at scale since joins mean shuffling data between slots; columnar storage keeps unaccessed nested fields free to ignore; and the data arrives atomically (an entry and its lines can't get separated). A **star schema** (fact table + dimension tables) still earns its place when dimensions are large, shared across many facts, and *change independently* — you don't want to rewrite a billion-row fact table because a cost-center description changed; a dimension update touches one small table. The pragmatic BigQuery guidance: denormalize aggressively for read-heavy, append-mostly data (fold small/stable dimensions right into the fact rows, or use nested structures for true parent-child data like entry→lines), and keep genuinely mutable, reusable dimensions as separate tables you join — a hybrid, not a purist choice either way. Also, since BigQuery storage is cheap relative to compute, "storing the same attribute redundantly" is usually the right trade against "shuffling a join every query." For ledger data specifically: journal header with nested lines is a natural fit and preserves the debit-credit grouping structurally.

**Follow-up they'll ask:** "How do you sum amounts across nested lines?" — `SELECT h.entry_id, SUM(l.amount) FROM entries h, UNNEST(h.lines) l GROUP BY h.entry_id` — comma-UNNEST is an implicit CROSS JOIN with the array.

**Red flag to avoid:** Reciting "always normalize / third normal form" — that's OLTP thinking; in BigQuery the join-shuffle cost changes the math.

### Q26: A production query got slow. Walk me through how you'd optimize it.

**Strong answer:** First, *measure before touching*: pull the job's **execution details** (query plan) and `INFORMATION_SCHEMA.JOBS` stats — bytes scanned, slot-milliseconds, stage timings, and shuffle bytes — to see whether the query is scan-bound, shuffle-bound, compute-bound, or just queued waiting for slots (contention looks like slowness but is a capacity problem). Then, in order of typical payoff: (1) **Scan less** — is the partition filter present and prunable (constant, on the raw partition column)? Are we selecting unneeded columns? Bytes-scanned dropping confirms it. (2) **Shuffle less** — find the stage with huge shuffle output; reduce data *before* the join (filter/aggregate early, join on what's needed), check for accidental many-to-many joins exploding rows (compare stage input vs output row counts — a stage emitting far more rows than it reads is the smoking gun). (3) **Skew** — one slot stuck while others finish means a hot key (NULLs or a dominant account); fix by filtering/salting or handling the hot key separately. (4) **Structural** — replace repeated re-computation with a materialized view or staged temp table; check clustering fits the filter columns; replace `ORDER BY` over huge results (a single-node sort at the end) with `LIMIT`-bounded or window-scoped ordering. (5) Only then consider **capacity** — more slots. The discipline: one change at a time, re-measure bytes/slot-ms after each, and keep the evidence — "I cut it from 1.2 TB scanned to 40 GB by fixing partition pruning" is the story interviewers want.

**Follow-up they'll ask:** "How do you spot skew in the plan?" — Stage timing shows max worker time vastly exceeding average/median worker time for one stage.

**Red flag to avoid:** Jumping straight to "add more slots" or rewriting SQL blind without reading the plan.

## 3. GCS → BigQuery pipeline patterns

### Q27: How would you lay out buckets/prefixes for a file-ingestion pipeline (landing/staging/archive)?

**Strong answer:** Three logical zones, whether as separate buckets or prefixes: **landing** — where the upstream system drops files, write-access for the producer only, minimal retention, treated as untrusted input; **staging/processing** — where the pipeline works on files it has picked up (decompressed, split, validated), fully owned by the pipeline's service account; **archive** — immutable, long-retention storage of the *original* files exactly as received, which in finance is your legal system-of-record for replays and audits. Within zones, date-partitioned, source-scoped prefixes: `gs://bucket/ledger/source=sap/dt=2026-07-14/filename.csv` — hive-style so external tables and humans can both navigate, and so a day's reprocess maps to one prefix. Key policies per zone: lifecycle rules (landing auto-deletes after N days; archive transitions to Nearline/Coldline/Archive storage classes as it ages — big cost savings for rarely-read compliance data); optionally bucket-lock/retention policies on archive for regulatory immutability; and uniform IAM so producers can't read other producers' data. Two operational details that pay off: the pipeline *moves* (copy+delete) files landing→staging→archive so a file's location tells you its processing state at a glance; and file naming carries a date + sequence/id so duplicates and re-deliveries are detectable by name before you even open the file.

**Follow-up they'll ask:** "Why archive the original file if the data's already in BigQuery?" — Because the file is the ground truth for disputes and replays: if a load bug is found months later, you reprocess from the untouched original — BigQuery time travel only covers days.

**Red flag to avoid:** One bucket, flat namespace, files deleted after load — no replay path, no audit trail.

### Q28: The upstream sends ZIP files. BigQuery can't load ZIPs — what do you do?

**Strong answer:** Correct — BigQuery load jobs cannot read ZIP archives; the only compression it reads natively for CSV/JSON is **gzip** (one member, `.csv.gz`), which it decompresses on the fly (though gzip files can't be split, so a single huge gzip loads on one worker — slower than uncompressed for very large files). ZIP is both a compression *and* an archive format (multiple files inside), so it needs an explicit decompress step: in our design, an Airflow task (or a Cloud Function for event-driven flows) downloads the ZIP from landing, extracts the members, and writes each extracted CSV to the staging prefix — then normal loads proceed per CSV. Practical considerations: stream the extraction rather than loading whole files into memory when files are large (Python's `zipfile` over a GCS file object, writing members back out in chunks); validate the member list against expectations (the daily ledger ZIP should contain a known set of files — a missing member is a data incident, not a shrug); handle nested directories and encoding of member names; be conscious of Composer worker disk/memory limits — for very large archives, run extraction on a Cloud Function/Cloud Run job sized for it instead of on Airflow workers, keeping Airflow as the orchestrator not the compute. If you can influence the producer, the best fix is upstream: ask for `.csv.gz` per file instead of ZIP — then the decompress step disappears entirely because BigQuery handles gzip natively.

**Follow-up they'll ask:** "Why not decompress inside BigQuery with a UDF or something?" — Load jobs read files as-is; there's no server-side unzip hook — decompression must happen before or during landing→staging.

**Red flag to avoid:** Confusing ZIP with gzip — saying "BigQuery reads zipped CSVs" without the distinction is a factual error interviewers catch instantly.

### Q29: File-arrival triggering: event-driven (Pub/Sub + Cloud Functions) vs schedule + sensor — compare them.

**Strong answer:** **Schedule + sensor:** the DAG runs on a cron-like schedule and a `GCSObjectExistenceSensor` waits for the expected file. Pros: dead simple, everything visible in one Airflow DAG, natural fit when the business process is inherently daily ("the ledger file for date D"), and the schedule itself documents the expectation — a timeout tells you the file is *late*, which is itself a signal. Cons: wasteful waiting (mitigated by reschedule/deferrable modes), latency up to a poke interval, and awkward for unpredictable or many-per-day arrivals. **Event-driven:** GCS bucket notifications publish an `OBJECT_FINALIZE` event to Pub/Sub the moment a file lands; a subscriber — a Cloud Function, or a push into Airflow via the stable REST API triggering a DAG run with the file path as config (or, in newer Airflow, dataset/asset-based scheduling — version-dependent) — starts processing immediately. Pros: zero waiting, scales to any arrival pattern, minimal latency. Cons: more moving parts (notification config, Pub/Sub, function, retries/DLQs), Pub/Sub is **at-least-once** so the consumer must dedupe (same event can fire twice — idempotent loading is mandatory), and "the file never arrived" produces *no event*, so you still need a separate absence/freshness alert — the failure mode is silence. My rule: daily, contractual, deadline-bound files → schedule + sensor, because the schedule encodes the contract and lateness is observable; ad-hoc, high-frequency, or many-source files → event-driven, with an independent completeness check. Hybrid is common: event-driven ingestion plus a scheduled end-of-day reconciliation DAG that verifies everything expected actually arrived.

**Follow-up they'll ask:** "How does the event-driven path detect a missing file?" — It can't by itself; you add a scheduled check ("by 06:00, have we processed file X for date D?") — absence needs a clock, not an event.

**Red flag to avoid:** Presenting event-driven as strictly superior — losing the "file is late/missing" signal is a real regression for contractual finance feeds.

### Q30: How do you achieve exactly-once loading of files into BigQuery? Describe your dedup strategy.

**Strong answer:** True exactly-once emerges from **at-least-once delivery + idempotent processing**, enforced at two levels. **File level:** keep a load-ledger — a small BigQuery (or metadata) table recording each processed file's identity: name, size, GCS generation number, a content hash if cheap, load timestamp, and target partition. Before loading, check the ledger; if this exact file (same name *and* generation/hash) was already loaded, skip — this defuses duplicate Pub/Sub events, sensor re-fires, and operator retries. GCS's **generation number** is the underrated tool here: a re-uploaded file with the same name gets a new generation, so you can distinguish "duplicate event for same bytes" (skip) from "producer re-sent a corrected file" (reprocess). **Row level:** loads go into a staging table (append is fine there), then publication into the final table is idempotent by construction — either partition overwrite (`WRITE_TRUNCATE` on `table$YYYYMMDD` when a file maps to a whole day) or a `MERGE` keyed on the business key (entry id + line number) with staging deduped first via `ROW_NUMBER()` keeping the latest. Belt-and-braces: a post-load assertion compares loaded row count against the file's line count (and sum-of-amounts against a control total if the feed provides one), so any duplication that slips through both layers is caught before publishing downstream. The interview-ready summary: dedupe at the *file* boundary with a processed-files ledger, make the *write* idempotent with partition overwrite or MERGE, and *verify* with counts — three independent layers.

**Follow-up they'll ask:** "The same logical file arrives twice with slightly different contents — which wins?" — That's a business rule, not a tech default: typically latest-by-generation wins with the earlier one archived and the discrepancy flagged, because a corrected resend is common in finance.

**Red flag to avoid:** Relying on "Airflow won't run it twice" — retries, clears, and backfills mean it absolutely will.

### Q31: How do you handle schema drift — the upstream adds, removes, or renames a column?

**Strong answer:** First, *detect before you break or, worse, silently mis-load*: a validation task reads the file header (or an external table's schema) and compares against the expected schema contract stored in config/version control — any difference raises a specific "schema drift" alert rather than a generic load failure. CSVs make this urgent because they're **positional**: if a column is inserted in the middle and you load by position, every subsequent column shifts and amounts land in the wrong fields *without any error* — the nastiest possible failure for ledger data, so header-vs-contract checking is non-negotiable. Then classify the drift: **additive** (new column at the end) is usually safe to handle automatically — BigQuery load jobs support schema-update options (`ALLOW_FIELD_ADDITION`) to extend the table, or you land into a stringy staging table that simply gains a column, and the new field flows as NULL-tolerant until modeled; **destructive** (removed/renamed/retyped column) must stop the pipeline for that feed — quarantine the file, alert, and involve a human, because guessing the producer's intent with financial data is how mis-postings happen. Structurally, the staging-with-lenient-types pattern absorbs most drift: ingestion rarely fails, and the typed staging→final transformation is where the contract is enforced explicitly with clear errors. Finally, treat the schema as a *versioned artifact*: contract files in git, changes reviewed with the upstream team, and the pipeline logs which contract version each load used — auditors and future-you both benefit.

**Follow-up they'll ask:** "Upstream renames `amt` to `amount` — walk me through your response." — Drift check fails and quarantines the file; confirm with the producer it's a rename not a semantic change; update the contract + mapping in staging→final SQL; reprocess the quarantined file; document the effective date of the change.

**Red flag to avoid:** "Autodetect handles new columns" — autodetect handles *guessing*, and silent positional shift in CSVs is exactly what it won't save you from.

### Q32: What data quality gates do you run before publishing data downstream?

**Strong answer:** Gates run *between* staging and final/publish — data that fails never becomes visible downstream, which is the entire point of the staging layer. Ours in rough order: (1) **Completeness** — file-level: all expected files for the date arrived; row-level: loaded count equals source count (file line count or a control/trailer record if the feed has one). (2) **Integrity** — business keys are non-null and unique (duplicate journal-line keys are a hard fail); mandatory fields (account, amount, currency, posting date) populated. (3) **Validity** — amounts parse as numeric with expected precision, dates fall in the expected period (a posting date two years in the future is a red flag), currency and account codes exist in reference data (foreign-key-style checks via anti-joins). (4) **Domain invariants** — the finance-specific ones: within each journal entry, debits equal credits; per-entity daily totals within tolerance of the source system's control totals. (5) **Reasonableness** — soft checks: row count within N% of trailing average, no sudden 10x in total absolute amount — these *warn* rather than block, catching upstream anomalies that are technically valid. Implementation: each gate is a SQL assertion (query returns violating rows; zero rows = pass) run as an Airflow task; hard-fail gates stop the DAG and quarantine, soft gates emit warnings to the team channel; every gate's result is logged to a checks table with the run id — so we can *prove* to auditors that the July 14 output passed all checks before it was forwarded. Frameworks like Great Expectations or dbt tests formalize this, but the SQL-assertions-as-tasks pattern is the essence.

**Follow-up they'll ask:** "Hard fail vs warn — how do you decide?" — Anything that would make downstream *wrong* (duplicates, unbalanced entries, count mismatch) hard-fails; anything that makes it *suspicious* (volume drift) warns — err toward hard-fail for ledger data.

**Red flag to avoid:** "We check row counts" as the whole answer — counts can match while every amount is in the wrong column.

### Q33: How do you reconcile source vs loaded data, and how do you safely reprocess a bad day?

**Strong answer:** **Reconciliation** compares independent measures of the same data at each hop: source file line count vs BigQuery load-job `outputRows` vs final-table count for that date's partition; and — more important for finance — *amount-level* controls: sum of debits, sum of credits, and hash-total or control-total from the feed's trailer record vs the loaded aggregates, per entity per day. Counts catch dropped/duplicated rows; sums catch corrupted values that counts miss; both are cheap SQL over one partition. Results land in a reconciliation table (date, feed, expected, actual, delta, status) that feeds a dashboard and alerting — a non-zero delta blocks the downstream forwarding task. **Safe reprocessing of a bad day** is a rehearsed procedure, not an improvisation: (1) *Contain* — pause or hold the downstream-forwarding task for that date so bad data stops propagating; notify downstream consumers of the hold. (2) *Diagnose* — using the archived original file (immutable, untouched) determine whether the fault was our pipeline (bug) or the source (bad file needing a resend). (3) *Repair* — fix the code or receive the corrected file into landing. (4) *Replay* — clear/re-trigger the Airflow run for that logical date; because writes are partition-scoped overwrites/MERGEs, the rerun replaces exactly that day and nothing else — idempotency is what makes this a routine action instead of a surgery. (5) *Verify* — reconciliation gates re-run automatically as part of the replay; only on green does forwarding resume. (6) *Record* — incident note with timeline and root cause, because in finance the *process* of correction is itself auditable. If downstream already consumed the bad day, you additionally coordinate their correction — which is why the forwarding gate in step 1 is worth its weight in gold.

**Follow-up they'll ask:** "What if the bad day is 3 weeks old and downstream has month-end reports on it?" — Then it's not just a replay, it's a *restatement*: same technical replay, plus formal communication of the delta to consumers and possibly an adjusting entry rather than a rewrite, per the finance team's policy — the pipeline supports both because archive + idempotent replays let you regenerate any date.

**Red flag to avoid:** "Delete the data and reload" without mentioning containment of downstream, verification, or the audit record — the SQL is the easy 20% of the job.

## 4. Finance / ledger domain

### Q34: What is a general ledger, and what are journal entries? Explain double-entry.

**Strong answer:** The general ledger (GL) is a company's central book of record: the complete collection of its **accounts** (cash, receivables, revenue, expenses, and thousands of granular ones identified by a chart of accounts), each accumulating the transactions that affect it. A **journal entry** is the atomic unit of change: it records one economic event as a set of **lines**, each line hitting one account with either a **debit** or a **credit** amount, plus metadata — posting date, entity, currency, description, source system, and a reference/document number. **Double-entry** is the invariant that makes accounting self-checking: every entry's total debits must exactly equal its total credits, because every event has two sides — buy a laptop with cash and you debit an asset account (equipment) and credit another asset account (cash); book revenue and you debit receivables, credit revenue. Debits and credits aren't "plus and minus" — they're the two sides of each account, and whether a debit increases or decreases the balance depends on account type (debits increase assets/expenses, credits increase liabilities/equity/revenue). For a data engineer this maps directly to data structures and checks: an entry is a header with 2+ lines (great fit for nested/repeated fields), the debits=credits rule is a per-entry SQL assertion you can and should enforce at load, and the GL table your pipeline builds is what accountants summarize into balances and financial statements. Sub-ledgers (AP, AR, fixed assets) hold transaction detail in source systems and post summarized entries into the GL — which is why our feed is called "ledger data" and why reconciling GL back to sub-ledger totals is a standing control.

**Follow-up they'll ask:** "One journal line has only a debit — valid?" — Individual *lines* carry one side each; the *entry* (the set of lines) must balance — a single-line entry can't balance and should be rejected.

**Red flag to avoid:** Saying debits are increases and credits are decreases universally — it depends on account type, and getting this wrong flags zero domain exposure.

### Q35: What is a trial balance and why does it matter to your pipeline?

**Strong answer:** A trial balance is a report listing every GL account with its total debits, total credits, and net balance as of a date — and its defining property is that the grand total of all debit balances equals the grand total of all credit balances, because if every journal entry balanced, the sum of everything must balance too. Accountants use it as the first sanity check before producing financial statements: an unbalanced trial balance means something structural is broken — a half-posted entry, a corrupted amount, a missed file. For the pipeline, it's the perfect *end-to-end* validation artifact: after loading a day, compute the trial balance from our loaded data (`SUM(debit), SUM(credit) GROUP BY account` plus grand totals) and (a) check it balances internally, and (b) compare it against the trial balance the *source system* produces — if the two match account-by-account, you have very strong evidence the load was complete and correct, far stronger than row counts, because it verifies the *amounts*. It also localizes problems: a mismatch confined to three accounts points you at the entries touching those accounts rather than the whole day. Note the limitation, which interviewers like you to know: a balanced trial balance proves *arithmetic* consistency, not *correctness* — an entry posted to the wrong account (or a whole entry missing entirely, since it removes equal debits and credits) still balances; that's why you reconcile against source totals too, not just check internal balance.

**Follow-up they'll ask:** "Trial balance vs balance sheet?" — Trial balance is the raw internal check listing all accounts; the balance sheet is a formal statement derived from it (assets/liabilities/equity) after adjustments and classification.

**Red flag to avoid:** Claiming a balanced trial balance proves the data is correct — it proves debits met credits, nothing more.

### Q36: What is a reconciliation break, and how do you find one with SQL?

**Strong answer:** A reconciliation break is a discrepancy between two records that should agree — source system vs our loaded GL, GL vs sub-ledger, our output vs what downstream received, or yesterday's closing balance vs today's opening. The SQL playbook is a **drill-down from aggregate to row**: (1) confirm and size the break at the top — `FULL OUTER JOIN` the two sides' daily totals per entity/account and select rows where amounts differ or one side is NULL (full outer matters: a missing account on one side *is* the break, and an inner join would hide it); (2) localize — same comparison at finer grain (account → account+currency → account+day) until the break isolates to a small slice; (3) row-match — join at the business-key level (entry id + line number) to classify each discrepancy into the three fundamental types: **missing** (in source, not loaded — dropped rows), **extra** (loaded, not in source — duplicates, usually a rerun artifact), and **different** (same key, different amount — truncation, encoding, sign flips, FX applied twice); (4) diagnose from the pattern — all breaks share one file? loading issue; amounts off by exactly 100x? decimal/precision bug; extras are exact duplicates? idempotency gap; one-sided entries? partial load cut mid-file. Two practical tools: `EXCEPT DISTINCT` between the two sides gives an instant diff of full rows, and comparing `SUM(amount)` alongside `COUNT(*)` distinguishes "wrong rows" from "wrong values." Every break found becomes a permanent automated check — reconciliation suites are accumulated scar tissue.

**Follow-up they'll ask:** "Counts match but sums differ by a tiny amount — first suspicion?" — Numeric precision: FLOAT64 rounding vs NUMERIC, or truncation of decimal places during CSV parsing — always store money as NUMERIC/BIGNUMERIC, never FLOAT.

**Red flag to avoid:** Starting at row-level diffing on millions of rows — always aggregate first, then drill; and never use INNER JOIN for reconciliation.

### Q37: What is period close, and how does it change what your pipeline must guarantee?

**Strong answer:** Period close (month-end/quarter-end/year-end close) is the finance process of finalizing the books for a period: all transactions posted, accruals and adjustments booked, reconciliations completed, sub-ledgers agreed to GL — and then the period is **locked**, after which its reported numbers must not change, because statements, regulatory filings, and management decisions are built on them. For the pipeline this creates concrete requirements. **Timing:** close runs on a tight calendar (working day 1, 2, 3...), so during close the pipeline's SLAs harden — a file late by four hours on a normal day is an annoyance; during close it delays the entire close chain, so alerting thresholds and on-call attention tighten. **Volume and shape:** close periods bring adjustment entries, reversals, and late postings dated to the closing period, so volumes spike and "posting date ≠ arrival date" becomes normal — the pipeline must route entries by *posting period*, not arrival date. **Immutability after lock:** once a period is closed, the pipeline must not rewrite its partitions — a correction to a closed period arrives as a *new adjusting entry in the open period* (or a formally governed prior-period adjustment), never as an in-place update; technically we protect this with checks that block writes to closed-period partitions outside a controlled restatement process. **Auditability:** close-period outputs are exactly what auditors sample, so lineage — which files, which loads, which checks produced this number — must be reconstructible. Understanding close is what separates "I move files" from "I support a financial process": the pipeline's calendar, controls, and immutability rules all derive from it.

**Follow-up they'll ask:** "A late file for a closed period arrives — what happens?" — It doesn't silently load into the closed period; it's flagged, and finance decides: post as current-period adjustment, or trigger the formal prior-period restatement process — the pipeline enforces that the choice is explicit.

**Red flag to avoid:** Treating all days as equal — not knowing that close changes SLAs, volumes, and write rules signals you've never sat near a finance team at month-end.

### Q38: Why do idempotency and auditability matter *more* in finance pipelines than elsewhere?

**Strong answer:** Because the failure modes have regulatory and monetary consequences, not just dashboard glitches. **Idempotency:** a duplicated load in a marketing pipeline inflates a chart; a duplicated load in a GL pipeline double-books entries, breaks the trial balance, flows into financial statements, and — if caught late — forces a restatement, which for a bank is a reportable event. Since retries, replays, and file re-deliveries are *normal* operations, only idempotent writes make routine operations safe; put differently, in finance idempotency isn't a best practice, it's a **control**. **Auditability:** banks operate under regulation (SOX-style controls, local regulators) requiring that reported numbers be traceable to source: for any figure, you must be able to show which file it came from, when it was loaded, by which job version, what validations passed, and who/what changed it since — which drives concrete engineering choices: immutable archived source files, load-audit tables (file, hash, generation, job id, timestamp, row counts), logged validation results per run, version-controlled pipeline code and schema contracts, and no manual, unlogged data edits in production — corrections happen through the pipeline so they leave a trail. There's also **segregation-of-duty** flavor: the person who can change pipeline code shouldn't be able to silently alter production data outside it. The compact framing for interviews: in most domains, bad data costs you trust; in finance it can cost you a regulator's attention — so the pipeline is built like evidence, not just plumbing.

**Follow-up they'll ask:** "Give one concrete auditability artifact you maintain." — The load-audit table: one row per file processed with hash, GCS generation, load job id, row counts, and check results — it answers "prove this number's origin" in one query.

**Red flag to avoid:** Generic "data quality is important" answers — name the mechanisms (immutable archive, audit tables, controlled corrections) or the answer is empty.

### Q39: How do you handle late adjustments and backdated entries?

**Strong answer:** Backdated entries — posted today but *effective* in a past date/period — are routine in accounting (accruals, corrections, reclassifications), so the pipeline must model **two dates** for every entry: the *posting/effective date* (which period the entry belongs to, driving which partition/report it affects) and the *load/received timestamp* (when we ingested it, driving audit and incremental processing). Confusing these is the classic bug: partitioning only by arrival date makes "give me July's entries" wrong the moment an August-arriving, July-dated entry exists. Handling depends on the target period's state: if the effective period is **open**, the entry flows normally into that period's data, and downstream aggregates for that period are re-derived (this is why balance tables are recomputed from entries rather than incrementally patched — recomputation is idempotent, patching accumulates drift); if the period is **closed**, the entry must not slip in silently — it's routed per finance policy (post to current open period as an adjustment, or a governed restatement), and the pipeline enforces this with closed-period write guards. Reporting-wise, this creates the "as-of" problem: "July's total *as we knew it* on Aug 1" differs from "July's total *as known* today" — the received-timestamp lets you answer both (bitemporal querying), which auditors and analysts genuinely ask for. Operationally: late entries should be visible, not just absorbed — a daily report of "entries received for prior periods" gives finance the heads-up that history moved. The one-line summary: model effective time and knowledge time separately, recompute rather than patch, and never let a closed period change without a controlled process.

**Follow-up they'll ask:** "How does this interact with your partitioning choice?" — Partition by *effective/posting* date (that's how data is queried and reprocessed), keep received-timestamp as a column — and note that a backdated entry means a rerun/merge into an *old* partition, which your idempotent write path already supports.

**Red flag to avoid:** "We just append it with today's date" — that's how period totals silently disagree with the source system forever.

## 5. Big data & Spark basics

### Q40: When would you use Spark/Dataproc instead of BigQuery, and vice versa?

**Strong answer:** Default to BigQuery when the work is expressible as SQL over structured data — it's serverless (no clusters to size or babysit), scales transparently, and for scan/aggregate/join workloads it's usually both faster to build and cheaper to operate for a small team. Reach for Spark (on Dataproc, GCP's managed Hadoop/Spark, or Dataproc Serverless) when you need what SQL can't give you: complex procedural transformations (custom parsing of messy files, per-record business logic in Python/Scala that would be tortured as SQL/UDFs), ML libraries and iterative algorithms, processing of non-tabular/binary data, fine control over the execution (custom partitioning, specific join strategies), or portability — Spark code runs on any cloud/on-prem, while BigQuery SQL is GCP-bound, which matters in a bank with multi-platform strategies. Cost model differs too: Dataproc bills for cluster VM uptime (ephemeral job-scoped clusters are the discipline — spin up, run, tear down), BigQuery bills per bytes scanned or slots — steady heavy transformation pipelines sometimes pencil out cheaper on Spark, ad-hoc analytics almost never do. The lines have blurred — version-dependent: BigQuery now runs Spark stored procedures and has BigQuery Studio notebooks, and Dataproc reads BigQuery tables via the connector (which uses the Storage Read API) — so hybrid designs are normal: Spark for the gnarly transformation, BigQuery for storage, SQL modeling, and serving. For a daily CSV-to-GL pipeline at our volumes, BigQuery alone is the right call; I'd introduce Spark only if a transformation genuinely fought SQL.

**Follow-up they'll ask:** "Your daily files grew 100x — does that change the answer?" — Not automatically: BigQuery load + SQL scales fine; Spark enters if the *transformation logic* becomes procedural, not because volume alone grew.

**Red flag to avoid:** "Spark is for big data, BigQuery is for small data" — both are for big data; the split is procedural-vs-SQL and operational model, not size.

### Q41: Explain partitioning and shuffle in Spark.

**Strong answer:** Spark splits a dataset into **partitions** — independent chunks processed in parallel, one task per partition per stage — so partition count and balance directly set your parallelism: too few partitions leaves cores idle, too many drowns you in task-scheduling overhead, and *skewed* partitions (one huge, rest small) make the whole stage wait for one straggler task. **Narrow** transformations (map, filter) work within a partition — no data movement, they pipeline together in one stage. **Wide** transformations (groupBy, join, distinct, repartition) need rows with the same key on the same partition, which forces a **shuffle**: every task writes its output bucketed by key hash to local disk, then the next stage's tasks fetch their bucket from *every* upstream task over the network — an all-to-all exchange involving serialization, disk, and network, which is why shuffles dominate most job runtimes and why stage boundaries in the Spark UI sit exactly at shuffles. Tuning revolves around shuffling less and shuffling well: filter/aggregate before wide ops; avoid repeated shuffles on the same key (partition once, reuse); size the shuffle partition count to the data (`spark.sql.shuffle.partitions` — the historical default of 200 fits almost nobody; Adaptive Query Execution in Spark 3 coalesces post-shuffle partitions automatically — version-dependent); and handle skew (AQE skew-join splitting, or salting hot keys). The one-breath summary: partitions are the unit of parallelism, shuffle is the price of grouping by key, and the craft is minimizing that price.

**Follow-up they'll ask:** "`repartition` vs `coalesce`?" — `repartition(n)` full-shuffles to n balanced partitions (can increase count); `coalesce(n)` merges existing partitions without a shuffle (decrease only, can be unbalanced) — coalesce is cheaper for reducing output file count.

**Red flag to avoid:** Hand-waving shuffle as "Spark moves data around" — name the mechanics: map-side write by key hash, reduce-side fetch, disk + network, stage boundary.

### Q42: What is a broadcast join and when does it help?

**Strong answer:** A normal distributed join shuffles *both* tables by the join key so matching rows meet on the same partition — two full network exchanges. A **broadcast join** skips that entirely when one side is small: Spark ships a full copy of the small table to every executor (broadcast), and each partition of the big table joins against its local copy — the big table never moves, no shuffle occurs, and the join becomes an in-memory hash lookup per partition. This is the single biggest join optimization when it applies, and it applies constantly in warehouse-shaped work: fact-to-dimension joins — a billion-row ledger-lines table joined to a 50k-row chart-of-accounts table should always broadcast the dimension. Spark auto-broadcasts below a size threshold (`spark.sql.autoBroadcastJoinThreshold`, default ~10 MB — version-dependent, and AQE can convert to broadcast at runtime once it sees actual sizes), or you force it with the `broadcast()` hint when statistics mislead the planner. The failure mode to respect: broadcasting something too big — every executor must hold the whole table in memory, so a "small" table that's actually 5 GB causes OOMs or painful broadcast time; and the small table is materialized to the driver first in classic broadcast, so driver memory matters too. Bonus: broadcast joins are also immune to join-key skew, since there's no shuffle to skew — a hot key just means more local lookups. BigQuery does the equivalent automatically (broadcast vs hash/shuffle join chosen by the optimizer), which is worth mentioning to connect the concepts.

**Follow-up they'll ask:** "Both tables are large but one becomes small after filtering — will Spark broadcast?" — With AQE (Spark 3+), yes — runtime statistics can switch the plan to broadcast; without it, the static planner may miss it, so filter early and hint.

**Red flag to avoid:** "Broadcast the smaller table" without the memory caveat — smaller than the other table isn't the bar; small enough to fit on every executor is.

### Q43: Compare Parquet and Avro with CSV — why do file formats matter?

**Strong answer:** CSV is text: no schema (types are guesswork), no compression by default, no column skipping (a reader parses every byte of every row), ambiguous parsing (delimiters in values, quoting, encodings, no standard for NULL vs empty), and no evolution story — it's the format you *receive*, not the format you *process*. **Parquet** is columnar: schema embedded in the file, values stored column-by-column with per-column encodings (dictionary, run-length) and compression, plus per-block min/max statistics — so engines read only needed columns and skip blocks that can't match a filter (predicate pushdown); it's the default for analytics — Spark reads/writes it natively and BigQuery both loads and exports it, with types preserved so there's no CSV-style parsing risk. **Avro** is row-oriented binary with a strong schema and first-class **schema evolution** (reader/writer schema resolution — add fields with defaults, readers old and new cope) — its sweet spot is *record streams and interchange*: Kafka payloads, write-heavy landing data, anywhere whole records are produced/consumed one at a time; it's a poor fit for analytics scans since you can't skip columns. Rule of thumb: row formats (Avro) for writing/moving records, columnar (Parquet/ORC) for reading/analyzing them. Concrete impact: the same dataset as Parquet is often 5–10x smaller than CSV and analytical reads touch a fraction of even that — which in bytes-scanned-billed systems is directly money. In our pipeline CSV exists only because the upstream sends it; the moment data lands in BigQuery it's in a columnar form (Capacitor), and any intermediate files we control should be Parquet or Avro, never CSV.

**Follow-up they'll ask:** "Why does BigQuery prefer Avro/Parquet loads over CSV?" — Self-describing schema (no autodetect gambling), binary types survive intact, better compression, and splittable/parallel loading — CSV loads are the slowest and most error-prone path.

**Red flag to avoid:** "Parquet is compressed CSV" — the columnar layout, statistics, and embedded schema are the point, not just compression.

### Q44: What is the small-files problem and how do you deal with it?

**Strong answer:** Distributed systems pay a **per-file** overhead — open, list, read metadata/footer, schedule a task — that's amortized over the file's contents; when data is fragmented into thousands of tiny files (KBs–few MBs), overhead dominates payload: listing a GCS prefix with 100k objects is slow before a single byte of data is read, Spark historically creates a task per file (or splits within files) so tiny files mean armies of trivial tasks whose scheduling costs more than their work, and Parquet's benefits (column blocks, statistics) barely materialize when each file holds a handful of rows. It arises naturally: streaming sinks writing every few seconds, over-parallelized Spark jobs writing one file per task (200 shuffle partitions → 200 files per run, every run), or per-entity/per-hour output layouts. Fixes on both ends. **Prevention:** write fewer, bigger files — `coalesce`/`repartition` before writing to target ~128 MB–1 GB per file, buffer/window streaming outputs, and question extreme directory granularity. **Cure:** compaction — periodic jobs that read the fragments and rewrite them as consolidated files (table formats like Delta/Iceberg have built-in compaction/`OPTIMIZE`; on raw GCS you roll your own rewrite). BigQuery-specific angles: native storage doesn't have this problem (Capacitor manages its own layout — one of the perks of letting the warehouse own storage), but it resurfaces at the edges — load jobs across thousands of tiny CSVs are slower (though one load job can take a wildcard of many files, which helps), and *external tables* over small-file prefixes query painfully. Our upstream sends a handful of daily files so we're safe by construction, but the ZIP-extraction step is where I'd watch it — an archive exploding into thousands of tiny members would be handled by consolidating during extraction.

**Follow-up they'll ask:** "What's a good target file size and why not just one giant file?" — Roughly 128 MB–1 GB for Parquet on object storage: big enough to amortize overhead, small enough to split/parallelize; one giant *unsplittable* file (e.g., gzip) serializes the read onto one worker.

**Red flag to avoid:** Only defining the problem — the interviewer wants coalesce-before-write and compaction as the two concrete levers.

## 6. Behavioral & narrative coaching

### Item 45: "Walk me through your project end-to-end." — the 90-second structure

**Coaching:** Rehearse a four-beat arc; each beat is 2–4 sentences, and lead with business context, not tools. **Beat 1 — Why (10s):** "I work on a finance data platform at HSBC — we produce the general-ledger data that downstream finance teams use for reporting and close, so correctness and deadlines are contractual, not nice-to-haves." **Beat 2 — Flow (30s):** "Upstream systems drop daily ledger extracts — CSVs, some zipped — into GCS landing buckets. Cloud Composer orchestrates the flow: sensors detect arrivals, we decompress and stage files, batch-load them into partitioned BigQuery staging tables with explicit schemas, run validation gates — completeness against control totals, debit-credit balance checks, dedup — and only then merge into the final GL tables and forward outputs downstream." **Beat 3 — Hard parts (30s):** pick TWO you can defend deeply, e.g., "The two problems I find most interesting: making everything idempotent — files get re-sent and DAGs get rerun, so every write is partition-scoped or MERGE-based so replaying any date is safe; and reconciliation — we prove loaded data against source counts and amount totals before anything is published, because in finance a silent discrepancy is worse than a loud failure." **Beat 4 — Your role (10s):** "I work across the ingestion DAGs and the validation checks — building and maintaining them and supporting the daily batch — and to really understand the full flow I rebuilt a working version of the pipeline end-to-end myself." **Match the verbs to your résumé exactly:** it says you *support, build, maintain, and develop* — so say that, not "I architected/owned it." A modest, precise claim you can defend beats a big one you can't; over-claiming here is the fastest way to get cornered on six months of tenure. Practice it aloud until it's ~90 seconds without rushing; the interviewer will interrupt with follow-ups — that's success, because you chose the beats they drill into.

**Red flag to avoid:** Starting with "so we have a DAG that…" — tool-first narration with no business frame reads junior regardless of content.

### Item 46: "You've only been on this project 6 months / you didn't build X" — handling it honestly

**Coaching:** Never bluff ownership — interviewers cross-examine, and one caught exaggeration poisons everything true you said. Keep every claim consistent with your résumé's verbs (*support, build, maintain, develop*) — the résumé is the contract; the interview must not exceed it. The winning posture has three moves. **(1) Own your slice precisely:** "I've been on this pipeline six months; I work hands-on across [the ingestion DAGs / the validation checks / the daily-batch support — whatever is true], and I've handled its production issues." Specific, bounded scope is *more* credible than vague breadth — and it matches what your résumé says, so there's nothing to catch you on. **(2) Show you understand the whole anyway:** "I wasn't there when the framework was built, but I've traced the full flow — I can explain why each design choice was made," and then *demonstrate* it with one insight, e.g., why loads are partition-overwrite rather than append. Understanding-without-authorship is a completely respectable senior trait — most engineers inherit systems. **(3) Play your ace — the rebuild:** "To close my own gaps, I rebuilt a working version of the whole pipeline end-to-end — GCS buckets, Composer DAGs, BigQuery loads, the validation layer — so I've personally implemented every stage even where production predates me." That converts the weakness into evidence of initiative, and it's the detail interviewers remember. Frame the rebuild as how you *learned the platform you support*, not as a separate job — that keeps it consistent with a résumé that has no separate personal-project line. If asked about a part you genuinely don't know: "That part I haven't worked hands-on; my understanding is [accurate summary], but I won't overclaim it" — then pivot to an adjacent thing you *do* know deeply. Honesty plus one deep spike beats fake breadth every time.

**Red flag to avoid:** The word "we" for everything — interviewers hear "we built" as "someone built"; use "I" for your work and name what wasn't yours.

### Item 47: "Tell me about a production failure."

**Coaching:** Use STAR but weight it toward diagnosis and prevention — the interviewer is evaluating how you think under failure, not the failure itself. Pick an incident (real, from your six months — a late/malformed file, a failed load, a reconciliation break are all perfect) and structure: **Situation** (one sentence: what broke and its business impact — "the morning GL load failed validation, putting the downstream delivery deadline at risk"); **Diagnosis** (the meat — show method: "alert fired → task logs → the load count didn't match the file's control total → traced to the upstream file being truncated mid-transfer" — narrate the *funnel* from symptom to cause, including a wrong turn if you had one, which adds credibility); **Action** ("we quarantined the file, notified upstream for a resend, and because our loads are idempotent, replaying the date after the resend was a standard clear-and-rerun, verified by the reconciliation gates before forwarding resumed"); **Result & prevention** ("delivered N hours late with downstream informed proactively; we added a file-size/completeness check at landing so truncation is caught at arrival rather than at validation"). Three qualities to project: calm sequencing (contain → diagnose → fix → verify), respect for process (downstream was told early; nothing was hand-edited), and the reflex that every incident ends with a new automated check. If you truly have no production incident, use one from your replica build or a near-miss — but say so honestly.

**Red flag to avoid:** A story where the fix is "I restarted it and it worked" or where blame lands on someone else — no diagnosis, no prevention, no learning.

### Item 48: "How do you validate data before forwarding it downstream?"

**Coaching:** This is your strongest technical-behavioral crossover — answer with the layered-gates story and concrete finance checks, and you'll sound like the owner of the validation layer. Structure the answer as layers: "Validation runs between staging and publish, so nothing failing checks is ever visible downstream. Layer one, **completeness**: every expected file arrived, and loaded row counts match the file's line counts and trailer control totals. Layer two, **integrity**: business keys unique and non-null — duplicates hard-fail. Layer three, **domain rules**: within every journal entry, debits equal credits; amounts are valid NUMERIC; posting dates fall in an expected period; account codes exist in reference data. Layer four, **reconciliation**: per-account, per-entity daily totals compared against the source system's — amounts, not just counts. Layer five, **reasonableness**: soft alerts on volume or total-amount drift versus trailing averages." Then add the two operational sentences that elevate it: "Hard-fail checks stop the DAG and quarantine the data; soft checks warn. Every check's result is written to an audit table per run — so we can prove, for any date, exactly what was verified before forwarding." If asked "did you build this?", apply Item 46: own what you own, and mention implementing the full validation layer in your replica.

**Red flag to avoid:** Answering only "row count checks" — for ledger data, counts-match-but-amounts-wrong is the failure mode that actually hurts, so amounts and balance rules must appear in your answer.

### Item 49: Questions YOU should ask the interviewer

**Coaching:** Your questions are scored — they reveal what you care about. Ask 2–3, chosen for the interviewer's role. **To an engineer/tech lead:** "What does your ingestion and orchestration stack look like, and what's the most painful part of it right now?" (invites shop-talk, shows you expect real problems); "How do you handle data quality and reconciliation — is it centralized or per-pipeline?" (signals your finance-grade instincts); "What does on-call/production support look like for the data team?" (shows operational maturity). **To a manager:** "What would success look like for this role in the first six months?"; "How is the team split between building new pipelines and running existing ones?"; "What's the growth path for data engineers here — deeper platform work or broader domain ownership?" **One differentiating question if the company is finance-adjacent:** "How do close cycles or regulatory deadlines shape your engineering calendar?" — almost nobody asks it, and it instantly marks you as someone who's lived it. Avoid: questions answered on the website, compensation questions in technical rounds (save for HR), and zero questions — "no, I'm good" reads as low interest. Prepare the questions beforehand and genuinely listen to the answers; a follow-up on their answer is worth more than a third prepared question.

**Red flag to avoid:** Generic "what's the culture like?" as your only question — it's a filler question and both of you know it.

### Item 50: Salary and notice-period basics (India market, generic guidance)

**Coaching:** Brief and practical. **Research first:** know the realistic band for a 4-YOE data engineer with GCP/BigQuery/Airflow skills in your city — triangulate from levels/salary aggregator sites, recruiter conversations, and peers; bands vary widely by company tier (service company vs product vs global bank vs startup), so anchor to the *target* company's tier, not your current one. **When asked current CTC / expected CTC:** you can share expectations as a range rather than a point ("I'm targeting the X–Y range based on the market for this skill set"), anchoring toward the top of your researched band; keep fixed-vs-variable in mind — compare offers on fixed pay and vesting reality, not headline CTC (joining bonuses and inflated variable components pad CTC without padding your bank account). Typical market movement for a strong switch at 4 YOE is significant, but quote your research, not folklore. **Notice period:** Indian notice periods commonly run 30–90 days; know yours exactly, know whether your employer permits **buyout** (you or the new employer pays salary in lieu of notice) and whether leave can offset it — a 90-day notice is a real hiring obstacle, so if buyout is possible, say so proactively: "my notice is 90 days, but buyout is available and I'm willing to use it" keeps you competitive against 30-day candidates. **Negotiation posture:** stay factual and warm; never bluff a competing offer you don't have; get the final offer in writing before resigning; and resign properly with documented notice — the finance/banking world is small and references matter.

**Red flag to avoid:** Naming a single precise expected number early with no research behind it — you either anchor low and lose money or anchor unjustifiably high and lose the offer; ranges backed by "market research for this stack" are safer on both sides.
